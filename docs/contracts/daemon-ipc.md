# Daemon IPC Contract

Contract version: **0.2.6** (see `CHANGELOG.md`). Original 0.1.0 baseline; 0.2.0 added the controller/controlled model; 0.2.1 the embedded engine, honest permissions and support commands; 0.2.2 refused links and withdrawn pairing requests; 0.2.3 a closed `link_error` vocabulary; 0.2.4 the controller's arrangement on controlled devices; 0.2.5 shortcut and remap-rule checks; 0.2.6 one-step permission setup and fixed network ports.

**Three transports, one contract** (see `README.md`): the desktop app calls the engine in-process (Tauri `flow_command(command, payload)` → result or `{code, message}` error; state arrives as `flow://event` events `{event, payload}`), `flow-daemon` serves the same over a loopback WebSocket, and the UI's mock implements both shapes in memory. The rest of this document uses the WebSocket envelope; the Tauri bridge carries the identical command names, payloads, results, errors and events.

**WebSocket: loopback TCP, `127.0.0.1:47823`** (`flow_core::ipc::IPC_PORT`, `FLOW_IPC_PORT` overrides). Served by `flow-daemon` always, and by the desktop app only with `FLOW_DEV_WS=1` (production has no local socket).

**Authentication (WebSocket only): a shared token.** `127.0.0.1` is reachable by *any* local process, including a browser tab's own `WebSocket` (which can set the subprotocol list but cannot read files). The engine generates a random token on first run (`~/.flow/ipc.token`, `FLOW_IPC_TOKEN_PATH` overrides) and every connection must present it as the WebSocket subprotocol (`Sec-WebSocket-Protocol`) or the handshake is rejected (`daemon/src/ipc/server.rs`). The UI's `WebSocketTransport` takes it from `?token=`. The in-process Tauri bridge needs no token because there is no socket.

**Status: implemented.** `daemon/src/ipc/{dispatch,events,server}.rs`; `daemon/tests/ipc_protocol.rs` is the end-to-end proof; `app/ui/src/client/mockEngine.ts` is the other implementation.

## The client interface

Everything the UI does with the engine goes through `FlowClient` (`app/ui/src/client/flowClient.ts`):

- **State** is pushed, never fetched. The client folds each event into one immutable `FlowState` (`getSnapshot`/`subscribe`, read with `useSyncExternalStore`).
- **Commands** are methods (`switchTo`, `removeDevice`, `startPairing`, `updateSettings`, `requestPermission`, `cancelReconnect`, …) returning a promise that resolves when the engine accepted the command (with the answer, for the few commands that have one) and rejects with `FlowCommandError(code, message)` when it refused. The effect shows up on the state, not in the promise.
- **Transports** (`Transport`: `connect`, `send(command, payload) → result`, `close`) are Tauri, WebSocket and Mock. Payload keys are `snake_case` on the wire; `mapper.ts` is the only place keys are converted.

Why events-out / commands-in: device state, link health and settings change because of what happens on the *other* computer, not only because of local commands. A pushed stream is the only shape that stays correct then.

## Wire envelope

```json
// UI -> engine
{ "id": "req-17", "command": "switch_to", "payload": { "target": "d2" } }

// engine -> UI, acknowledging req-17
{ "id": "req-17", "ok": true }
// ... or with an answer (get_keymap, reveal_config_dir, export_diagnostics, open_permission_settings)
{ "id": "req-18", "ok": true, "result": { "path": "/home/me/.config/flow-daemon/keymaps" } }
{ "id": "req-19", "ok": false, "error": { "code": "device_not_found", "message": "no device d2" } }

// engine -> UI, unsolicited state push (no id)
{ "event": "devices_changed", "payload": [ /* Device[] */ ] }
```

- `id` is generated by the UI and echoed in exactly one ack. The answer of a command is **`result`** everywhere (engine, WebSocket, Tauri, mock).
- Ten state events: `devices_changed`, `link_state_changed`, `pairing_session_changed`, `settings_changed`, `permission_changed`, `incoming_pairing_request_changed`, `control_state_changed`, `remap_rules_changed`, `screen_layout_changed`, `diagnostics_changed`. They are sent on connect in that order (`incoming_pairing_request_changed` is `null` until a request exists) and then on every change, so connecting *is* the initial fetch. Over Tauri there is no connect, so the UI sends **`resync`** after subscribing and the engine re-sends all ten; `resync` also works on the WebSocket.
- Error `code` is stable and machine-readable; `message` is a developer string and is not matched on. Codes: `device_not_found`, `device_not_switchable`, `device_not_removable`, `pairing_in_progress`, `pairing_not_active`, `pairing_not_ready`, `candidate_not_found`, `invalid_switch_key`, `switch_key_needs_modifier`, `switch_key_conflict`, `permission_already_granted`, `permission_setup_cancelled`, `permission_setup_unavailable`, `permission_setup_failed`, `permission_not_found`, `link_not_recoverable`, `not_reconnecting`, `pairing_request_not_found`, `not_controller`, `not_controlled`, `no_controller`, `invalid_remap_rule`, `duplicate_remap_rule`, `invalid_layout`, `invalid_payload`, `unknown_command`, `internal_error`. The UI maps codes to friendly copy (`app/ui/src/copy.ts`) and falls back to a generic message for unknown ones.

## Commands

| Command | Payload | Preconditions | Effect |
|---|---|---|---|
| `switch_to` | `{ target: "local" \| DeviceId }` | This device is a controller (`not_controller`), the device exists (`device_not_found`) and has a live link (`device_not_switchable`). | The controller's input goes to `target`; the previous active device becomes `inactive`. Emits `devices_changed` and `control_state_changed`. |
| `switch_active_device` | `{ device_id }` | As `switch_to` (`d1` means `local`). | Alias of `switch_to`, kept for 0.1 clients. |
| `release_control` | — | This device is controlled (`not_controlled`) with a linked controller (`no_controller`). | Asks the controller for this machine back; the controller decides and returns to its own screen. |
| `set_role` | `{ role }` | — | Persists the role, closes live links so peers renegotiate. Emits `settings_changed`, `control_state_changed`. |
| `set_screen_layout` | `{ layout: ScreenLayout }` | Controller; layout includes `d1`, no overlaps/duplicates/empty screens, every other screen is a known device (`invalid_layout`). | Persisted; adjacency for edge switching derives from touching edges. Emits `screen_layout_changed`. The controller also sends it to each linked controlled device. |
| `set_remap_rules` | `{ rules: RemapRule[] }` | Every rule valid (`invalid_remap_rule`); at most one rule per `from` key and `when_target_os` (`duplicate_remap_rule`). | Saved to `<keymap dir>/remap.toml`, applied to forwarding immediately. Emits `remap_rules_changed`. |
| `get_keymap` | `{ os }` | — | Answers with the effective keymap for `os` (embedded defaults merged with the user's override file) as `{ id, ok: true, result }`. |
| `remove_device` | `{ device_id }` | Device exists and isn't the local device ("This device" is never removable). | Device dropped from the list. Emits `devices_changed`. |
| `start_pairing` | — | `PairingSession.stage == idle` | Session moves to `searching`; candidates arrive as they're discovered. Emits `pairing_session_changed`. |
| `cancel_pairing` | — | Session is not `idle`. | Session resets to `idle`, in-flight request abandoned. |
| `pair_with_candidate` | `{ candidate_id }` | Session `stage == found`, candidate in the list. | Session moves through `requesting` → `paired` (or `failed`); on success the paired device is added via `devices_changed` too. |
| `set_switch_key` | `SwitchKeyBinding` | Binding non-empty (`invalid_switch_key`); a typing key needs `Ctrl`, `Alt` or `Meta` (`switch_key_needs_modifier`); not the same keys as `return_home_key` (`switch_key_conflict`). See `data-model.md` `SwitchKeyBinding`. | Settings updated. Emits `settings_changed`. |
| `update_settings` | `SettingsPatch` (any subset of `FlowSettings` fields) | A `switch_key` or `return_home_key` it sets follows the `set_switch_key` rules; nothing changes (not even `role`) when one is refused. | Merged into current settings. Emits `settings_changed`. |
| `reset_settings` | — | — | Settings restored to defaults. Emits `settings_changed`. |
| `request_permission` | — | `PermissionStatus.granted == false` | Gets everything missing granted the best way the OS allows: macOS shows its Accessibility and Input Monitoring prompts; Linux runs the one-time system setup (input devices, `uinput`, firewall) behind one administrator prompt (`pkexec`) and acks once it finished, so it can take as long as the person takes to type their password. The engine re-probes and `permission_changed` follows. Fails with `permission_setup_cancelled` (prompt dismissed), `permission_setup_unavailable` (no `pkexec`/polkit agent; the item's `how_to_fix` has a terminal command) or `permission_setup_failed` (a step failed; `message` ends with the reason in plain words). |
| `resync` | — | — | Re-sends all ten state events (the Tauri equivalent of connecting). |
| `recheck_permissions` | — | — | Re-runs the OS permission probe now ("Check Again"); result arrives as `permission_changed`. |
| `open_permission_settings` | `{ name }` | `name` is a `PermissionStatus.items[].name` (`permission_not_found`). | Answers `{ url }` for the OS settings page (`null` if none); the desktop app opens it. |
| `reveal_config_dir` | — | — | Answers `{ path }` of the keymap/config folder (created if missing); the desktop app opens it in the file manager. |
| `export_diagnostics` | — | — | Writes a JSON bundle (settings, devices without keys, link/permission state, diagnostics, recent log tail) to `<data dir>/diagnostics/` and answers `{ path }`. |
| `cancel_reconnect` | — | Link state is `reconnecting` (`not_reconnecting`). | Stops redialling after a lost link until `retry_connection`; link becomes `disconnected`. |
| `retry_connection` | — | `DaemonLinkState` is `disconnected` or `error` | Moves link state to `connecting`; actual recovery to `connected` follows the normal link-health path (automatic on a real daemon, e.g. discovery redialing a trusted peer) and shows up via `link_state_changed` like any other transition — this command never jumps straight to `connected` itself. |
| `respond_to_pairing_request` | `{ request_id, decision: "accept" \| "reject" }` | A request with `request_id` is currently pending. | Unblocks the daemon's pairing handshake with that decision and clears the pending request (emits `incoming_pairing_request_changed: null`). On `accept`, the peer is added and appears via `devices_changed`. Error `pairing_request_not_found` if no such request is pending (already answered / timed out / withdrawn). |

`SettingsPatch` is a plain partial object — only the keys being changed are sent, e.g. `{ "share_mouse": false }`. This is why `update_settings` exists separately from `set_switch_key`: the switch key has its own recording UI/flow (§ below) and warrants its own command for validation (rejecting an empty or already-reserved binding) rather than being folded into the generic patch.

Desktop-shell commands: the desktop app answers `open_main_window {route?, sheet?}` (tray popover → main window) and `restart_app` (relaunch Flow, offered when `PermissionStatus.restart_required`) itself; they never reach the engine, and any other client gets `unknown_command`.

## State machines

### Pairing (`PairingSession.stage`)

```
idle --start_pairing--> searching --(candidate found)--> found
found --pair_with_candidate--> requesting --(peer accepts)--> paired --(auto, ~1.6s)--> idle
requesting --(peer rejects / times out)--> failed --(auto, ~1.6s)--> idle
any non-idle state --cancel_pairing--> idle
```

The mock's timings (`searching` → `found` after ~1.2s, `requesting` → `paired` after ~1.5s, auto-return to `idle` after ~1.6s) are **not** part of the contract — a real daemon's pairing latency depends on actual network discovery and the human on the other end clicking "Accept". What *is* part of the contract: the stage sequence itself, and that `paired` and `failed` are terminal-but-transient (the UI always returns to `idle` on its own; the daemon doesn't need a UI ack to leave `paired`/`failed`).

### Incoming pairing requests

Independent of `PairingSession` (which models only the *initiating*
side). When another device connects to this daemon's peer listener
and is not already trusted, the daemon publishes an
`IncomingPairingRequest` on `watchIncomingPairingRequest()` and
waits up to ~30s for `respond_to_pairing_request`. No connected UI,
no answer within the timeout, or a second request arriving while one
is pending ⇒ the daemon rejects that request and the initiator sees
a normal pairing failure. If the initiator cancels (`cancel_pairing`
closes its connection) while the request is pending, the request is
withdrawn: `incoming_pairing_request_changed` goes back to `null`. Exactly one request is surfaced at a time;
the stream is `null` whenever none is pending.

### Switching

Roles are static; the **active screen** exists only on the controller (`ControlState.active_screen`, `"local"` or a device id).

```
controller:  local --switch hotkey / edge / switch_to--> remote(d) --hotkey / return-home / edge / release / link loss--> local
controlled:  idle --Enter--> entered --Leave / disconnect / heartbeat timeout--> idle   (ControlState.entered)
```

- Hotkey: the switch key cycles `local -> d1 -> d2 -> ... -> local` over controlled peers with a live link; the optional return-home key jumps to `local`. Both work while the controller's input is hidden from its own OS.
- `screen_layout_changed` is *this computer's own* arrangement on a controller (editable). On a controlled device it is the *controller's* arrangement, as the controller last sent it: read-only, in memory only, `d1` plus the controller's device id; just `d1` while none has arrived.
- Edges: with a `ScreenLayout`, pushing the pointer through an edge that has a neighbour switches to it (`edge_switching`, `edge_switch_delay_ms`).
- A link between two controllers or two controlled devices is refused: the device gets `link_error: "role_conflict"` (`"protocol_mismatch"` for a v1 peer). The device's `role`/`os` show what the peer announced, the link state becomes `error`, and the engine does not redial that peer until a role changes (the side that changes dials the other).
- Link loss while a peer is active returns the controller to `local`.
- `devices_changed` always has exactly one `active` device: the active screen's.

### Link health (`DaemonLinkState`)

```
connecting --(daemon reachable)--> connected
connected --(active link drops)--> reconnecting --(recovered)--> connected
connected --(active link drops, not retrying)--> disconnected
disconnected --(user retries / daemon recovers)--> connecting
any --(input-capture permission missing)--> permissionRequired --(request_permission granted)--> connected
any --(non-permission failure)--> error --(user retries)--> connecting
any --(link refused: role_conflict / protocol_mismatch)--> error --(a role changes, the link comes up)--> connected
```

## What's deliberately out of scope for 0.1.0

- **Multi-hop / >2 device topologies beyond a flat device list** — the contract already supports an arbitrary number of `Device` entries, but no daemon-side behavior (e.g. mouse-position-based switching) is assumed.
- **Authentication/encryption handshake details** — vision.md §17 covers this for the daemon-to-daemon transport; this local contract assumes the IPC channel itself is only reachable by the local user (Unix socket permissions / named pipe ACLs), not that it carries its own crypto.
- **Diagnostics** were out of scope for 0.1.0; since 0.2.0 the daemon measures switch latency (p50/p95), events forwarded/dropped and uptime and publishes them as `diagnostics_changed`.
