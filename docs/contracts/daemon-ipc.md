# Daemon IPC Contract

Contract version: **0.1.0**. This is the shape of the local control channel between the Flutter UI and the daemon (`docs/product/vision.md` §9) — commands the UI sends, state the daemon pushes back. The actual transport (Unix domain socket, named pipe, local TCP) is still undecided per the vision doc; everything here is transport-agnostic and just assumes a bidirectional message stream carrying JSON.

Today this contract is realized entirely by `flutter/lib/data/mock_daemon_repository.dart`. There is no wire format in use yet — the JSON here is the target shape for when one exists, kept alongside the Dart interface so the two can't silently drift.

## The interface

Everything the UI does with the daemon goes through one Dart interface:

```dart
abstract class DaemonRepository {
  // State streams — the daemon pushes, the UI only ever reads.
  Stream<List<Device>> watchDevices();
  Stream<DaemonLinkState> watchLinkState();
  Stream<PairingSession> watchPairingSession();
  Stream<FlowSettings> watchSettings();
  Stream<PermissionStatus> watchPermission();

  // Commands — the UI asks, the daemon acts and the result shows up
  // through the streams above, not through the returned Future's value.
  // The Future only resolves/rejects to say the command was accepted or
  // rejected; it never carries new state.
  Future<void> switchActiveDevice(String deviceId);
  Future<void> removeDevice(String deviceId);
  Future<void> startPairing();
  Future<void> cancelPairing();
  Future<void> pairWithCandidate(String candidateId);
  Future<void> setSwitchKey(SwitchKeyBinding binding);
  Future<void> updateSettings(SettingsPatch patch);
  Future<void> resetSettings();
  Future<void> requestPermission();
}
```

Why streams-out / commands-in rather than request/response for everything: device state, link health, and settings can all change because of what's happening on the *other* computer (vision.md §13, "active state should be synchronized between connected devices"), not just because of a local command. A stream is the only shape that's still correct when the daemon on the other machine is the one that caused the change. Commands stay `Future<void>` (fire-and-confirm) because their effect is always observable on a stream — a second return channel for the same data would be a second source of truth.

## Wire envelope (target shape, not yet implemented)

```json
// UI -> daemon
{ "id": "req-17", "command": "switch_active_device", "payload": { "device_id": "d2" } }

// daemon -> UI, acknowledging req-17
{ "id": "req-17", "ok": true }
{ "id": "req-19", "ok": false, "error": { "code": "device_not_found", "message": "no device d2" } }

// daemon -> UI, unsolicited state push (no id)
{ "event": "devices_changed", "payload": [ /* Device[] */ ] }
```

- `id` on a command is generated by the UI and echoed back in exactly one ack; it's how the UI resolves the right `Future`, not a general request/response pairing (there is no `get_devices` command — see below).
- Every `watch*` stream corresponds to one `event` name pushed whenever that slice of state changes: `devices_changed`, `link_state_changed`, `pairing_session_changed`, `settings_changed`, `permission_changed`. The daemon sends one on connect for each, so the UI never needs an explicit "give me the current state" command — connecting to the channel and subscribing *is* the initial fetch.
- Error `code` is a stable machine-readable string (`device_not_found`, `pairing_not_active`, `permission_denied`, `invalid_switch_key`, …); `message` is human-readable and not matched on.

## Commands

| Command | Payload | Preconditions | Effect |
|---|---|---|---|
| `switch_active_device` | `{ device_id }` | Device exists, state is `inactive` or `connected`. | Target device moves toward `active`; previous active device moves to `inactive`. Emits `devices_changed`. |
| `remove_device` | `{ device_id }` | Device exists and isn't the local device ("This device" is never removable). | Device dropped from the list. Emits `devices_changed`. |
| `start_pairing` | — | `PairingSession.stage == idle` | Session moves to `searching`; candidates arrive as they're discovered. Emits `pairing_session_changed`. |
| `cancel_pairing` | — | Session is not `idle`. | Session resets to `idle`, in-flight request abandoned. |
| `pair_with_candidate` | `{ candidate_id }` | Session `stage == found`, candidate in the list. | Session moves through `requesting` → `paired` (or `failed`); on success the paired device is added via `devices_changed` too. |
| `set_switch_key` | `SwitchKeyBinding` | Binding non-empty. | Settings updated. Emits `settings_changed`. |
| `update_settings` | `SettingsPatch` (any subset of `FlowSettings` fields) | — | Merged into current settings. Emits `settings_changed`. |
| `reset_settings` | — | — | Settings restored to defaults. Emits `settings_changed`. |
| `request_permission` | — | `PermissionStatus.granted == false` | Triggers the OS permission prompt; result reflected via `permission_changed`. |

`SettingsPatch` is a plain partial object — only the keys being changed are sent, e.g. `{ "share_mouse": false }`. This is why `update_settings` exists separately from `set_switch_key`: the switch key has its own recording UI/flow (§ below) and warrants its own command for validation (rejecting an empty or already-reserved binding) rather than being folded into the generic patch.

## State machines

### Pairing (`PairingSession.stage`)

```
idle --start_pairing--> searching --(candidate found)--> found
found --pair_with_candidate--> requesting --(peer accepts)--> paired --(auto, ~1.6s)--> idle
requesting --(peer rejects / times out)--> failed --(auto, ~1.6s)--> idle
any non-idle state --cancel_pairing--> idle
```

The mock's timings (`searching` → `found` after ~1.2s, `requesting` → `paired` after ~1.5s, auto-return to `idle` after ~1.6s) are **not** part of the contract — a real daemon's pairing latency depends on actual network discovery and the human on the other end clicking "Accept". What *is* part of the contract: the stage sequence itself, and that `paired` and `failed` are terminal-but-transient (the UI always returns to `idle` on its own; the daemon doesn't need a UI ack to leave `paired`/`failed`).

### Switching (`Device.state` on `switch_active_device`)

```
target: inactive|connected --switch_active_device--> pairing-free direct hop --> active
previous active: active --> inactive
```

Switching is not modeled as its own stage in this contract — unlike pairing, the UI does not need an intermediate "switching…" device state to render correctly (a debounced/disabled row while the command's `Future` is in flight is a UI concern, not a wire state). If real switching over a network transport turns out to need a visible in-between state, that's a `0.2.0` addition, not a `0.1.0` reinterpretation.

### Link health (`DaemonLinkState`)

```
connecting --(daemon reachable)--> connected
connected --(active link drops)--> reconnecting --(recovered)--> connected
connected --(active link drops, not retrying)--> disconnected
disconnected --(user retries / daemon recovers)--> connecting
any --(input-capture permission missing)--> permissionRequired --(request_permission granted)--> connected
any --(non-permission failure)--> error --(user retries)--> connecting
```

## What's deliberately out of scope for 0.1.0

- **Multi-hop / >2 device topologies beyond a flat device list** — the contract already supports an arbitrary number of `Device` entries, but no daemon-side behavior (e.g. mouse-position-based switching) is assumed.
- **Authentication/encryption handshake details** — vision.md §17 covers this for the daemon-to-daemon transport; this local contract assumes the IPC channel itself is only reachable by the local user (Unix socket permissions / named pipe ACLs), not that it carries its own crypto.
- **Diagnostics data** (the Advanced section's "average switch time, dropped input" line) — currently static copy in the UI, not sourced from the daemon. Wiring it up is a later contract version once the daemon actually measures those numbers.
